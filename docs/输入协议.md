# 输入协议：怎么把「预期结果」发给本程序

> 完整命令与配置项见 **[命令与配置手册](命令与配置手册.md)**；本文件只讲报文格式与连接方向。

本程序需要两类信息才能测一条用例：

| 信息 | 从哪来 | 用途 |
| --- | --- | --- |
| **采集信息 + 预期结果** | 闸机 / 你的测试程序推送（本文件） | 待测系统的输入 + 判定基准 |
| **待测系统运行日志** | WebSocket 推流 **或** 日志文件 | 推断实际结果 |

> 实际结果**不需要你发**，程序自己从日志里推断：
> `会话ID[x]-节点y执行失败` → 不允许通行（节点 y）；`旅客[z]离开通道` → 允许通行。

---

## 一、两种连接方向，二选一

### 方式 A：本程序当客户端（`gate.mode: client`，默认）

你的闸机/测试程序**开一个 WebSocket 服务端**，本程序连过去。适合闸机本来就提供服务的情况。

```yaml
gate:
  mode: client
  url: ws://127.0.0.1:8765/gate
```

### 方式 B：本程序当服务端（`gate.mode: server`）—— 测试程序更省事

本程序监听端口，你的测试程序作为**客户端**连上来推用例。不用自己写服务端。

```yaml
gate:
  mode: server
  listen_host: 127.0.0.1
  listen_port: 8765
  listen_path: /gate
```

连 `ws://127.0.0.1:8765/gate` 即可。两种方式**消息格式完全一致**。

### 方式 B½：`gate.mode: both` —— 两边都收，谁发都能收到（推荐先试）

不确定对方到底往哪个方向发（是"广播给已连上来的客户端"，还是"主动连你"）时，用 both：
本程序**同时**去连 `gate.url`，并监听 `listen_port`，两个方向的消息都进同一条流水线。

```yaml
gate:
  mode: both
  url: ws://127.0.0.1:1880          # 我们主动连它（跟测试程序连的是同一个地址）
  listen_host: 0.0.0.0              # 同时开这个端口等它连进来
  listen_port: 8765
  listen_path: /gate
  send_ack: false                   # 别回执，避免把数据写进对方的流程
```

> 注意：both 模式下"连出去"和"监听"是两个独立动作，互不影响；哪边先来消息就用哪边。

### 方式 B⅔：对方字段名不一样 → 用 `gate.field_map` 翻译（不改对方程序）

如果对方（例如 Node-RED 的流程）发的是它自己的 JSON 结构，你又不能改它，就在本地翻译：

```yaml
gate:
  field_map:
    case_id: msg.payload.id            # 右边是对方消息里的点路径，支持 a.b.c
    allow_pass: msg.payload.allow      # true/false、"允许"/"不允许"、1/0 都认
    failed_node: msg.payload.node
    cert_no: msg.payload.idCard        # 用来和日志里的 旅客[xxx] 对上号
    passenger_name: msg.payload.name
```

定位字段名的办法：先跑一次
`python tools\check_channels.py -c config.yaml --wait 60 --save-raw gate_raw.jsonl`，
`gate_raw.jsonl` 里就是对方的原始报文，照着填即可。映射结果会覆盖同名顶层字段，
其余字段原样保留（所以"整条消息当 capture"的兜底仍然有效）。

### 方式 C：HTTP 直接 POST（完全不用 WebSocket，最省事）

如果 WebSocket 的方向老是搞反（**注意：WebSocket 是"谁发谁推"，你连上一个
"别人正在收数据"的中继端口，是收不到任何东西的**），那就用 HTTP 推 ——
只要 `report.serve: true`（默认就是），本程序自带的 HTTP 服务就能收用例：

```bash
# Windows 命令行（用 curl.exe，PowerShell 里 curl 是别名，行为不一样）
curl.exe -X POST http://127.0.0.1:8767/api/case ^
  -H "Content-Type: application/json" ^
  -d "{\"case_id\":\"C-1\",\"expected\":{\"allow_pass\":true},\"capture\":{\"cert_no\":\"110101\"}}"
```

```python
# 测试程序里就三行
import json, urllib.request
req = urllib.request.Request(
    "http://127.0.0.1:8767/api/case",
    data=json.dumps(case).encode("utf-8"),
    headers={"Content-Type": "application/json"},
)
print(urllib.request.urlopen(req).read().decode("utf-8"))   # {"accepted": true, ...}
```

* 端口就是 `report.port`（默认 8767），路径 `/api/case`（也接受 `/api/cases`、`/case`、`/gate`）；
* 消息内容与 WebSocket **完全一样**，也可以一次 POST 一个**用例数组**批量推；
* 返回 `{"accepted": true}` = 已进流水线；`{"accepted": false, "error"/"message": ...}` = 被拒（比如缺 `expected.allow_pass`）；
* 支持 CORS，浏览器里直接 `fetch()` 也行。

## 二、一条用例的格式

一条 WebSocket **文本帧**，内容是 JSON：

```json
{
  "type": "gate.capture",
  "case_id": "C-000123",
  "timestamp": "2026-02-14T10:00:00+08:00",
  "gate_id": "G01",
  "expected": {
    "allow_pass": false,
    "failed_node": "证件核验"
  },
  "capture": {
    "passenger_name": "李四",
    "cert_type": "ID_CARD",
    "cert_no": "310101198805124321",
    "photo_base64": "data:image/jpeg;base64,/9j/4AAQ..."
  }
}
```

### 字段说明

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `type` | 否 | 固定 `gate.capture`（也接受 `capture`/`case`/`test.case`，省略也行） |
| `expected.allow_pass` | **是** | 预期是否允许通行 |
| `expected.failed_node` | 否 | 预期**不允许通行**时，应该在哪个节点失败（如 `证件核验`、`人脸比对`） |
| `capture` | **是** | 闸机采集的证件信息，原样透传给分析模型 |
| `capture.cert_no` / `capture.passenger_name` | **强烈建议** | 程序用它们匹配日志里的 `旅客[xxx]`，**是定位"这条用例的日志"的关键** |
| `session_id` | 否 | **直接指定会话ID**（也可放在 `capture.session_id`）。不给就自动从日志的「创建新会话」推断 |
| `capture.photo_base64` | 否 | 照片，支持 `data URL` / 纯 base64 / `http(s)` 地址 / 本地文件路径 |
| `case_id` | 否 | 唯一编号，省略自动生成（建议给，报告和面板都按它命名） |
| `timestamp` / `gate_id` | 否 | 原样保留在报告里 |

## 二½、会话ID 和 证号 分别对应什么

这是两条**独立的关联链**，别混在一起：

| 名字 | 从哪来 | 代码里的位置 | 用途 |
| --- | --- | --- | --- |
| **会话ID** | **待测系统日志**（不是用例消息） | 正则捕获组 `(?P<sid>…)`：<br>① `[流程引擎]创建新会话<sid>`（`patterns.session_create`）<br>② `会话ID[<sid>]-节点<node>执行失败`（`patterns.node_failure`） | 把「一条流程」圈起来：**日志切片区间** + 失败节点归属 |
| **证号**（`capture.cert_no`） | **用例消息** | `judge.passenger_keys` 里第一个命中的字段 | 去日志里找 `旅客[<内容包含证号>]`，从而**把用例和会话关联起来** |
| 姓名（`capture.passenger_name`） | 用例消息 | 同上（`passenger_keys` 的第 3 项） | 证号没打印时的备选关联键 |

对应关系图：

```
用例消息 ──capture.cert_no/乘客姓名──┐
                                    ├─ 在日志里找 旅客[xxx]  → 定位到某条流程
日志     ──[流程引擎]创建新会话<sid>─┘                              │
            └─ 会话ID[<sid>]-节点<node>执行失败 ──────────────────┘
                                    同一 sid 串起来 → 该用例的实际结果
```

细节：

* **匹配是"包含"而不是"相等"**：日志写 `旅客[张三]`、用例给 `passenger_name=张三` → 命中；
  日志写 `旅客[张三/110101199003071234]`、用例给 `cert_no=110101199003071234` → 也命中。
* **默认认这些字段**（`judge.passenger_keys`，按顺序尝试）：
  `cert_no`、`id_no`、`passenger_name`、`name`、`passengerName`、`certNo`。字段不同就改这里。
* **失败节点**由 `node_failure` 的 `(?P<node>…)` 捕获，与 `expected.failed_node` 比对。
* **日志切片**：从 `[流程引擎]创建新会话<sid>` 到**整个日志中最后一次出现该 sid**（可配
  `run.slice_include_passenger_lines` 把 `旅客[...]` 行也纳入）。
* 如果日志里**不打印证号/姓名**：可以在消息里直接给 `session_id`（推荐），或打开
  `run.single_session_fallback: true`（只在"严格晚于本次采集且唯一"时才归属）。

给了 `session_id` 时：

```json
{
  "case_id": "C-9",
  "session_id": "S0003",
  "expected": {"allow_pass": false, "failed_node": "证件核验"},
  "capture": {"cert_no": "440301199512258765"}
}
```

日志里只要出现 `会话ID[S0003]-节点证件核验执行失败`，就直接定案（不再靠旅客标识猜）。

### `allow_pass` 的写法很宽松

以下都能识别：

```json
{"allow_pass": true}      {"allow_pass": "true"}     {"allow_pass": 1}
{"allow_pass": "允许"}    {"allow_pass": "允许通行"}  {"allow_pass": "pass"}
{"allow_pass": false}     {"allow_pass": "false"}    {"allow_pass": 0}
{"allow_pass": "不允许"}  {"allow_pass": "拒绝"}      {"allow_pass": "deny"}
```

### 最简可用消息

只有两个必填项就够了：

```json
{
  "expected": {"allow_pass": true},
  "capture": {"passenger_name": "张三", "cert_no": "110101199003071234"}
}
```

也支持**扁平写法**（不用 `expected`/`capture` 嵌套）：

```json
{
  "allow_pass": true,
  "cert_no": "110101199003071234",
  "passenger_name": "张三"
}
```
此时顶层除 `type/case_id/timestamp/expected/capture` 之外的字段全部当作采集信息。

## 二¾、一轮十几条消息：怎么知道哪几条是同一轮

真实现场（Node-RED 当闸机模拟器）常见形态：**一轮测试会发十几条 WebSocket 消息**，
其中只有**一条**带预期结果，其余是设备/命令应答（`START_COLLECTION`、`READER_GET_BY_MRZ`、
`FACE_MATCH` …）。这些消息都带同一个 `serial`。

本程序的处理方式：

1. **非用例报文安静忽略** —— 没有 `expected.allow_pass` 的消息既不算用例、也不算"协议错误"，
   只计入"忽略的非用例报文"（心跳里能看到）。
2. **按 `serial` 归轮**，把"这一轮第一条消息到达时的日志行号"记下来；
   等带预期结果的那条到了，**用那个更早的行号当日志切片起点** ——
   否则切片会从这一轮中间开始，很可能漏掉 `[流程引擎]创建新会话…` 那几行，导致会话匹配失败。
3. `serial` 含 `_` 时只取前半段比较：`serial_123` 与 `serial_456` 视为**同一轮**。

配置：

```yaml
gate:
  # 按顺序取第一个非空值作为"轮次键"
  round_keys: [serial, requestId, capture.cert_no, cert_no]
  # 轮次键含 "_" 时只取前半段；不想切就写 null
  round_split: '_'
  round_ttl_seconds: 600      # 多久没消息就忘掉这条轮次记录
```

> 同一条用例（同一个 `case_id`）只应出现一次；一轮结束后该轮的记录会被清掉，
> 下一轮即使 `serial` 前缀相同也会重新开始计时。

### 唯一标识：用 `serial`，不要用用例号/证号

* **用例号**（`case_id`）会被重复测多次，**证号**也可能重复 —— 都不能当唯一键；
* 本程序以 **完整 `serial`** 作为唯一序号：
  * 产物目录：`runs/<批次>/cases/<用例号>__<serial>/`（同一用例测两次不会互相覆盖）；
  * `case.json` 里同时写 `case_id`（用例号）与 `serial`（唯一序号）；
  * 报告、BI 大屏都会显示 serial；
* 归轮仍按 serial 的**前缀**（`serial_1` 与 `serial_2` 视为同一轮），
  但**唯一性用完整 serial** —— 两者不冲突。

### 这一轮的消息会被保存下来

每条闸机通道报文都会留档，并且在用例判定后**把整轮消息复制进用例目录**：

| 文件 | 内容 |
| --- | --- |
| `runs/<批次>/gate_raw.jsonl` | 本次运行收到的**每一条**原始报文（全量，含 base64 照片） |
| `runs/<批次>/cases/<case_id>/gate_messages.jsonl` | **这一轮**发给被测系统/从 Node-RED 来的消息，按时间顺序；`brief` 是去掉 base64 后的精简版 |
| `runs/<批次>/cases/<case_id>/case.json` → `gate` | 轮次（serial）、消息条数、**命令序列** |

用例**不通过**时会自动交给 DeepSeek Harness：提示词里明确要求它先看
`gate_messages.jsonl` 的**命令序列**（例如"少了 `CB_PASSENGER_LEAVE`，被测系统当然不会
出现「离开通道」"），再结合日志和源码定位问题。报告里也有「四、闸机通道消息」一节。

## 三、回执（可选）
本程序收到用例后会回一条确认（`gate.send_ack: true` 时）：

```json
{"type": "gate.ack", "case_id": "C-000123", "status": "accepted", "reason": ""}
```

格式不对时：`{"status": "rejected", "reason": "闸机消息缺少 expected.allow_pass（是否允许通行）"}`。

> 回执只是提示，**测试不会因为回执失败而中断**。

## 五、常见错误

| 现象 | 原因 |
| --- | --- |
| 控制台报「闸机消息不符合协议，已忽略」 | 缺 `expected.allow_pass`，或 JSON 不合法 |
| 用例一直超时、报告里没有日志 | `capture` 里没给 `cert_no`/`passenger_name`，日志里又找不到这个人 → 加字段，或设 `run.single_session_fallback: true` |
| 判定结果永远是「不允许通行」 | `patterns.node_failure` 正则和真实日志不一致 → 按 `logs.txt` 原文调正则 |
| 服务端模式起不来 | 端口被占用 → 改 `gate.listen_port`；看日志里「无法监听」那行 |
| 一条用例都收不到 | 客户端模式：地址/路径不对；服务端模式：测试程序连的地址不是 `listen_host:listen_port` |
| **连上了但一条消息都没有** | 十有八九是这个端口本来就**不是发给你的**：它是个中继/接收端，数据由发送方推给它，它只交给自己的上游连接，不会转发给后来连上的客户端。三种解法：① 改 `gate.mode: server`，让发送方连你；② 加 `gate.subscription`（有些中继要先订阅）；③ 直接用 **HTTP POST `/api/case`**（见方式 C） |
| 日志明明有内容，正则却 0 命中 | 日志编码不是 UTF-8（`����` 乱码就是这么来的）→ 把 `logs.file.encoding` 设为 `auto`；用 `python tools\check_channels.py -c config.yaml` 会直接告诉你真实编码，并把"可能相关"的真实日志行打出来 |

> 排查工具：`python tools\check_channels.py -c config.yaml --wait 30`
> 会分别报告闸机通道能不能连、连上有没有数据，日志文件编码与三条正则的命中次数。
>
> **消息格式对不上怎么办**（对方发的是它自己的格式，而你不想改它）：
> 加 `--save-raw gate_raw.jsonl` 把原始报文完整留档，再把它发给我，按它的真实字段适配解析即可：
>
> ```bat
> python tools\check_channels.py -c config.yaml --wait 60 --save-raw gate_raw.jsonl
> ```
>
> 正式运行时也会自动把每条闸机报文写进 `runs\<批次>\gate_raw.jsonl`，排查不用重跑。

## 六、判定规则速查（程序内部）

```
日志出现  会话ID[xx]-节点yy执行失败   → 实际：不允许通行，失败节点 = yy
日志出现  旅客[zz]离开通道           → 实际：允许通行
```

**用例通过的唯一标准**：`是否允许通行` 与 `失败节点名称` 都和预期一致。

日志归属：从 `[流程引擎]创建新会话<会话ID>` 开始，到最后一次出现该会话 ID 的行结束；
用 `capture` 里的证件号/姓名匹配 `旅客[...]` 来认领会话。

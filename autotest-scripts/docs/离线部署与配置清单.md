# 离线部署与配置清单

> 完整命令与配置项（含默认值）见 **[命令与配置手册](命令与配置手册.md)**；本文件只讲"怎么把这个东西搬过去跑起来"。

本文回答两件事：**离线怎么装**、**装完要配什么**。

---

## 一、离线包里有什么

`vendor/` 目录由 `tools/prepare_offline_bundle.py` 生成，随项目一起拷到离线机：

| 目录                     | 内容                                                                              | 为什么需要                                             | 体积    |
| ------------------------ | --------------------------------------------------------------------------------- | ------------------------------------------------------ | ------- |
| `vendor/python/`       | `websockets`、`PyYAML`、`rich`、`markdown-it-py`、`Pygments`、`mdurl` | 离线机不能`pip install`，程序启动时优先从这里 import | ~7 MB   |
| `vendor/node/node.exe` | 便携 Node.js 运行时                                                               | 离线机没装 node 也能调 DeepSeek Harness                | ~89 MB  |
| `vendor/dsh/`          | DeepSeek Harness 完整运行树（含`node_modules`）                                 | 失败分析靠它跑                                         | ~1.5 GB |
| `vendor/manifest.json` | 打包清单：版本、来源、链接数、自检结果                                            | 出问题先看这个                                         | 几 KB   |

> 只要「测试 + 报告」不要「自动分析」，可以只留 `vendor/python/`，其余删掉，
> 用 `--no-dsh` 运行，体积降到 7 MB。见下面第三种运行模式。

**各方的版本（本次打包结果）**

| 组件                       | 版本                                                 |
| -------------------------- | ---------------------------------------------------- |
| Python                     | 3.10+（本机用 3.13.12 打包，纯 Python 包跨版本可用） |
| websockets / PyYAML / rich | 17.3 / 6.0.3 / 15.0.0                                |
| Node.js                    | v24.20.0（随包）                                     |
| DeepSeek Harness           | `apps/cli/lib/bin.js`，`headless` profile        |

## 二、部署步骤

### 1. 在联网机（现在这台）打离线包

```bat
cd /d D:\Work\Project\auto
python tools\prepare_offline_bundle.py
```

脚本会：拷 Python 依赖 → 拷 `node.exe` → 用 robocopy 拷 DSH 运行树 → **重建 6200+ 个
pnpm junction** → 自检（用包里的 node 跑一次 `--dump-default-config`，不需要网络和 API Key）。
最后打印 `manifest.json` 路径和体积。

打包工具参数：

| 参数              | 作用                                            |
| ----------------- | ----------------------------------------------- |
| （无）            | 完整包：Python 依赖 + node + DSH                |
| `--no-dsh`      | 只要 Python 依赖（测试+报告离线可用，约 7 MB）  |
| `--skip-node`   | 目标机已装 Node.js，不打包`node.exe`          |
| `--dest <路径>` | 输出到别处（默认`./vendor`）                  |
| `--relink`      | **搬到新路径后**重建链接（离线机上必跑）  |
| `--finalize`    | 复制已完成时只补做「统计 + 自检 + 写 manifest」 |
| `--no-verify`   | 跳过自检                                        |

本次实际打包结果（可直接对照）：

```
[python] websockets 17.3 / PyYAML 6.0.3 / rich 15.0.0 / markdown-it-py 4.2.0 / Pygments 2.20.0 / mdurl 0.1.2
[node]   v24.20.0
[dsh]    69738 files / 1561.3 MB，链接 6205 个（指向包外 0 个）
[verify] bundle 内 DSH 自检：通过（exit=0）
```

### 2. 整个项目目录拷到离线机

把 `D:\Work\Project\auto` **整个目录**（含 `vendor\`）拷过去。U 盘 / 内网共享都行。

**想先打成 zip 传？** 用专门工具，别用资源管理器右键压缩：

```bat
python tools\make_archive.py                 :: → dist\auto-<时间>.zip，约 2 MB
python tools\make_archive.py --with-node     :: 额外带便携 node（+约 25 MB）
python tools\make_archive.py --with-runs     :: 额外带 runs 里的样例产物
```

> zip 里**不含** `vendor/dsh`：那棵树里有 6200+ 个 junction，右键压缩会被递归跟进，
> 体积爆炸甚至卡死，解压后链接也全废。目标机已装好 DSH 时本来就不需要它；
> 真要搬完整离线包，请**直接拷目录**，拷完在目标机跑 `--relink`。

### 3. ⚠️ 改过路径就必须重定位链接

Windows 的 junction 只能存**绝对路径**。如果离线机上的目录路径和原来不一样
（几乎肯定不一样），先跑一次：

```bat
cd /d <离线机上的项目目录>
python tools\prepare_offline_bundle.py --relink
```

它会读 `vendor\manifest.json` 里记录的旧位置，把 6200+ 个链接全部改指到新位置，然后
再自检一遍。**这一步只要 1~2 分钟，漏了它 DSH 一定起不来。**

> 如果项目在离线机上的路径和联网机**完全一致**，可以跳过这一步。

**如果 `--relink` 报「共 0 个链接」**（自检跟着报 `Cannot find package ...`）：说明
junction 在传输过程中被弄丢了（zip / 镜像 / 部分同步工具不保留 reparse point）。
这时 `--relink` 无能为力（它只能改写已有链接的目标），换用：

```bat
python tools\prepare_offline_bundle.py --restore-links
```

它按 `vendor\links.json` 把链接**重建**出来（目标都是相对路径，重建后放哪都行）。
详见 [故障修复-junction丢失.md](故障修复-junction丢失.md)。

> 更省事的做法：**目标机已装好 DSH 时压根不用传 `vendor/dsh`** —— 配置里用命令模式
> （`dsh.command: dsh` + `dsh.cli_js: null`）即可，1.6 GB 可以直接删掉。

### 4. 自检

```bat
python tools\verify_offline.py
```

逐项检查：vendor 依赖是否生效、node/DSH 运行树是否完整、凭据在不在、目录可写不。
加 `--check-endpoint` 还会 TCP 探测模型端点通不通。结论一目了然：

```
结论：[ OK ] 全部通过，可以离线运行
```

### 5. 填配置（见下一节）

改 `config.offline.yaml` 里标了 `【必改】` 的几项。

### 6. 启动

```bat
run_offline.cmd
```

它会自动把 `vendor\python` 加进 `PYTHONPATH`（用 `py -3`/自装 python 都行，
也可以 `set PYTHON_EXE=D:\Python311\python.exe`）。

## 三、要配什么（配置清单）

配置文件：**`config.offline.yaml`**（离线/内网部署用）；联网开发时可用 `config.yaml` / `config.selftest.yaml`。

### 先看这个：最少要配的几项

**如果你的机器上已经装好 DSH、模型和 Key 也配好了（你的情况），全部配置就这些：**

| # | 配置项                     | 填什么                                                 |
| - | -------------------------- | ------------------------------------------------------ |
| 1 | `gate.url`               | 闸机程序的 WebSocket 地址                              |
| 2 | `logs.url`               | 待测系统日志的 WebSocket 地址                          |
| 3 | `patterns.*`（三条正则） | **用真实日志核对一遍**，不改也能先跑，看结果再调 |
| 4 | `fix.repo_path`          | 待测系统代码仓库路径；留空 = 只分析不改代码            |

**就这 4 项。** `dsh` 那一段一个字都不用改（模型/API/Key 沿用 DSH 自己的配置），
Python 依赖也不用管（`vendor/python` 已就位，`run_offline.cmd` 自动加载）。

> 想让 `vendor/` 只有 8 MB（不带 node 和 DSH）：打包时加 `--no-dsh`，然后删掉
> `vendor/dsh`、`vendor/node`。因为你机器上的 DSH 已经能用了，那 1.5 GB 是给"裸机"准备的。

下面 A–F 是完整清单，只有"必改"和你会用到的"按需"才需要关注。

### A. 必改：三条连接

| 配置项                              | 说明                                                        | 示例                                     |
| ----------------------------------- | ----------------------------------------------------------- | ---------------------------------------- |
| `gate.url`                        | 闸机程序的 WebSocket 地址（本程序是**客户端**去连它） | `ws://127.0.0.1:8765/gate`             |
| `logs.url`                        | 待测系统日志的 WebSocket 地址                               | `ws://127.0.0.1:8766/logs`             |
| `gate.headers` / `logs.headers` | 需要鉴权时填握手头                                          | `{Authorization: 'Bearer xxx'}`        |
| `gate.subscription`               | 中继/网关要求先"订阅"才转发时填                             | `{type: subscribe, topic: case}`       |
| `logs.subscription`               | 连上后要先发订阅报文时填                                    | `{action: subscribe, topic: gate.log}` |
| `logs.message_format`             | 日志消息格式：`auto`/`text`/`json`                    | 纯文本行留`auto`                       |
| `logs.text_fields`                | JSON 包体里正文的字段名（按顺序试）                         | `[line, text, message, data.line]`     |

**如果日志是读文件的**（`logs.source: file`）：只需 `logs.file.path`，编码保持默认的
`auto` 即可（自动识别 UTF-8 / GBK；填错编码会让中文变乱码、正则全部落空）。

**如果 WS 连上了却一条消息都没有**：这个端口多半是"发给别人的中继"，WebSocket 不会
把别人的数据转发给新连上的客户端。三条出路：

1. 反过来：`gate.mode: server`（本程序监听，测试程序连进来推）；
2. 加 `gate.subscription`（有些中继要先订阅）；
3. 完全不碰 WebSocket：程序运行时用 HTTP 推，测试程序里就三行代码：

```python
import json, urllib.request
req = urllib.request.Request(
    "http://127.0.0.1:8767/api/case",                      # 端口 = report.port
    data=json.dumps(case).encode("utf-8"),
    headers={"Content-Type": "application/json"},
)
print(urllib.request.urlopen(req).read().decode("utf-8"))  # {"accepted": true}
```

> 一条命令把上面这些全查一遍：`python tools\check_channels.py -c config.yaml --wait 30`

### B. 必改：一条日志正则（关键！）

判定全靠这三条正则，**务必用真实日志核对一遍**：

| 配置项                      | 默认匹配                      | 何时要改           |
| --------------------------- | ----------------------------- | ------------------ |
| `patterns.session_create` | `[流程引擎]创建新会话<sid>` | 会话起始行格式不同 |
| `patterns.node_failure`   | `会话ID[x]-节点y执行失败`   | 节点失败文案不同   |
| `patterns.passenger_exit` | `旅客[z]离开通道`           | 通行成功文案不同   |

核对办法：先用 `--no-dsh` 跑一条用例，打开
`runs\<批次>\cases\<case_id>\logs.txt`，确认原文能被匹配上，`case.json` 里
`actual.allow_pass` / `actual.failed_node` 是否正确。

### C. 必改/按需：自动修复

| 配置项                  | 说明                                                                                         |
| ----------------------- | -------------------------------------------------------------------------------------------- |
| `fix.repo_path`       | 待测系统代码仓库本地路径，例如`D:/Work/Project/gate-system`。**留空=只分析不改代码** |
| `fix.push`            | 离线机通常没远端 → 保持`false`（只提交本地分支）；有内网 Git 时改 `true`                |
| `fix.branch_template` | 分支名模板，默认`{time}-修复{node}error` → `20261020-153012-修复证件核验error`          |
| `fix.remote`          | 推送用的远端名，默认`origin`                                                               |
| `dsh.allow_code_fix`  | `false` = 只给建议不改代码                                                                 |

### D. 模型端点与凭据 —— **机器上已装好 DSH 的话，这一节全都不用配**

程序只做一件事：调用一次 `dsh --profile headless "<提示词>"`。**模型是哪个、API 地址是什么、
Key 存在哪，全由 DSH 自己决定**（读它的 home：`DSH_HOME` 环境变量或 `%USERPROFILE%\.dsh`）。
所以只要你的机器上 `dsh` 能正常跑、`dsh` 里模型已经配好，这里**三项一个都不用填**：

| 配置项            | 已装 DSH 的机器            | 说明                                                        |
| ----------------- | -------------------------- | ----------------------------------------------------------- |
| `dsh.command`   | `dsh`（默认）            | 前提：命令行里`dsh --help` 有输出。不在 PATH 就填完整路径 |
| `dsh.dsh_home`  | **`null`（别改）** | null = 沿用 DSH 自己的 home，也就是你已配好的模型与 Key     |
| `dsh.base_url`  | **`null`（别改）** | DSH 里配过了，再填就是覆盖它                                |
| `dsh.extra_env` | `{}`（默认）             | 只有需要走代理时才填                                        |

验证只要一条命令：

```bat
dsh --profile headless --dump-default-config
```

能打印出配置树，就说明"能被本程序调用"。启动横幅里的 `Harness 分析` 一行也会显示
`命令模式就绪：<dsh 路径>（home=...）`，`模型/凭据` 一行只是**提示**（不阻断）。

> 只有在两种情况下才需要动这节：① `dsh` 不在 PATH（填 `dsh.command` 完整路径，或改用
> 下面的脚本模式）；② 机器上根本没有 DSH，用的是本仓库打出来的离线包。

**情况 B：机器上没有 DSH，用离线包（`vendor/`）**

| 配置项           | 填法                                                                                        |
| ---------------- | ------------------------------------------------------------------------------------------- |
| `dsh.cli_js`   | `./vendor/dsh/apps/cli/lib/bin.js`（填了它，`command` 自动忽略）                        |
| `dsh.node_exe` | `./vendor/node/node.exe`                                                                  |
| `dsh.dsh_home` | `null`，或指向你初始化好并有凭据的 home                                                   |
| 凭据             | 把联网机配好的`.dsh` 拷到离线机 `%USERPROFILE%\.dsh`，或设环境变量 `DEEPSEEK_API_KEY` |

**情况 C：机器完全断网**

`dsh.enabled: false` 或启动加 `--no-dsh` —— 测试+报告照跑，失败用例入队落盘；
之后拿 `runs` 目录到联网机 `--analyze-only` 集中分析。

### E. 按需：判定与产物

| 配置项                            | 说明                                                                         |
| --------------------------------- | ---------------------------------------------------------------------------- |
| `judge.node_aliases`            | 节点名对不上时做映射，例如`{证照核验: 证件核验}`                           |
| `judge.passenger_keys`          | 用采集信息哪些字段匹配`旅客[xxx]`，默认 `cert_no`、`passenger_name` 等 |
| `run.case_timeout_seconds`      | 单条用例等日志结论的上限，默认 25s（现场跑一条用例的时长 ×1.5 左右）        |
| `report.photo_fields`           | 采集信息里照片字段名，支持 base64 / data URL / http URL / 本地路径           |
| `report.dashboard`              | BI 面板：产物目录生成 `dashboard.html`（自动刷新）+ `dashboard.json`          |
| `logs.source`                   | `ws`（默认）或 `file`；用 file 时配 `logs.file.path` 持续跟随日志文件         |
| `gate.mode`                     | `client`（默认，去连闸机）或 `server`（自己监听，测试程序连进来推）            |
| `dsh.node_exe` / `dsh.cli_js` | 已指向`./vendor/...`，**除非你把 vendor 放到别处，否则别动**         |

### F. 不用配的东西

* Python 依赖 —— 已 vendored，`run_offline.cmd` 自动加 `PYTHONPATH`；
* `pip install` —— 不需要，离线机完全不用 pip；
* Node.js —— 已随包带 `vendor/node/node.exe`（目标机已有 node 也可以 `--skip-node` 打包）。

## 四、三种运行模式

| 模式                     | 命令                               | 适用                                    |
| ------------------------ | ---------------------------------- | --------------------------------------- |
| ① 完整：测试 + 失败分析 | `run_offline.cmd`                | 离线机可达模型端点（内网网关/私有部署） |
| ② 只跑测试 + 报告       | `run_offline.cmd --no-dsh`       | 完全断网。失败用例仍会入队落盘          |
| ③ 只消费已有队列        | `run_offline.cmd --analyze-only` | 把`runs` 目录带回联网机，集中分析     |

模式②→③ 是推荐组合：**离线机负责跑测试、留证据；联网机负责耗时的模型分析。**
队列是磁盘上的 JSON（`runs/_queue/pending/*.json`），用例产物（`case.json`/`logs.txt`/`photo.*`）
都在同目录树里，整个 `runs` 拷过去即可继续：

```bat
:: 联网机
set DSH_OUT=D:\from-offline\runs
python run_autotest.py -c config.offline.yaml --analyze-only
```

（若 `runs` 不在默认位置，改 `run.work_dir` 指过去，或直接拷进项目目录。）

## 六、常见问题

**连上了但一条用例都收不到（WS 没数据下来）**
这个端口通常是"发给别人的中继"：WebSocket 是点对点推送，服务端不会把它发给上游连接的
数据再广播给后来连上的客户端。改 `gate.mode: server` 让发送方连你，或加 `gate.subscription`，
或直接用 HTTP：`POST http://127.0.0.1:8767/api/case`。先跑
`python tools\check_channels.py -c config.yaml --wait 30` 看它到底有没有数据。

**日志明明有内容，却判不出结论 / 正则 0 命中**
编码不对（中文 Windows 的日志多是 GBK，用 UTF-8 解就成 `����`）。把
`logs.file.encoding` 设成 `auto`（默认就是）；`tools\check_channels.py` 会直接报出真实编码，
并把"可能相关的真实日志行"打出来，照着改正则即可。

**DSH 起不来 / `MISSING_CREDENTIAL`**
`python tools\verify_offline.py` 会指出是「CLI 找不到」还是「没有 API Key」。凭据两条路：
拷 `%USERPROFILE%\.dsh`，或设 `DEEPSEEK_API_KEY` 环境变量。

**`--dump-default-config` 报 ENOENT / 找不到模块**
十有八九是忘了 `--relink`（目录换路径了，junction 还指向老路径）。重跑一次即可。

**分析报「端点不可达」**
`verify_offline.py --check-endpoint` 确认；离线机不通就切模式②，之后用模式③在联网机分析。

**分析报 `max_completion_tokens=X cannot be greater than max_model_len=Y`**
这是 DSH 认为的模型容量比端点实际支持的大（`llm-deepseek` 默认按 256k 上下文算输出上限）。
在配置里声明真实容量即可，程序会用 `dsh --patch` 覆盖，**不改动 DSH 自身配置**：

```yaml
dsh:
  context_window: 128000   # 端点真实的上下文长度
  max_tokens: 32768        # 允许的输出上限
  # provider / model 留空 → 自动从 `dsh --dump-config` 识别
```

生效后日志里会有：

```
已生成模型容量 patch：provider=deepseek-official，model=deepseek-v4-flash，
maxTokens=32768，contextWindow=128000（llm-deepseek 覆盖插件级 maxTokens/defaultContextWindow）
```

实现方式（可对照排查）：先跑 `dsh --dump-config` 取当前组合，再按插件生成覆盖 ——
`llm-deepseek` 改插件级 `maxTokens` / `defaultContextWindow`；若 route 由 `llm-pi-ai`
的 `providers.<route>` 声明，则**回写该 route 的完整配置**（只改 models 的容量字段），
因为 patch 里 `providers.<route>` 是整体替换，漏掉 `api`/`baseURL` 会让 DSH 起不来。
patch 文件留在 `cases/<case_id>/dsh-model-capacity.patch.yml`，`analysis.json` 的
`harness.patch` 也会记下它，便于复现。也可以直接在 DSH 自己的模型配置里把 `maxTokens` 改小。

**日志能连但一条用例都不判定**
先看 `logs.txt` 有没有内容；再看 `patterns` 三条正则是否匹配真实日志；最后看
`judge.passenger_keys` 里的证件号/姓名是否真的出现在日志里（不行就设
`run.single_session_fallback: true`，或把字段名改成日志里实际打印的）。

**推送失败 `Please make sure you have the correct access rights`**
离线机没有远端就该 `fix.push: false`；要推就先把仓库的 remote 配好，并确认 git 凭据可用。

**体积太大**
只要测试+报告：删掉 `vendor/dsh`、`vendor/node`，用 `--no-dsh`，只剩 7 MB。

**不要把 `.dsh` 或 `DEEPSEEK_API_KEY` 提交进代码库**
`.gitignore` 已排除 `vendor/`、`.dsh-home/`、`runs*/`；拷 `.dsh` 时也别放进项目目录内。

**`run_offline.cmd` 一闪而过 / 卡住不动**
`.cmd`/`.bat` 必须**保持纯 ASCII**：cmd.exe 用 OEM 代码页逐行解析批处理，UTF-8 中文注释会让它
错行解析（这正是本仓库里 `run_offline.cmd` 注释全是英文的原因）。自己加注释时请用英文，
或把中文放备注文件里。需要中文输出时靠 `chcp 65001` + `PYTHONUTF8=1`（脚本里已经加好）。

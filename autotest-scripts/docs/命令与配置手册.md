# 命令与配置手册（完整版）

本文件是**唯一权威清单**：所有可执行命令、所有配置项（含默认值）、产物目录、判定规则、
以及现场常见问题的对应操作，都在这里。配置项与代码实现一一对应（`autotest/config.py`）。

- 只想快点跑起来 → [二、常用命令速查](#二常用命令速查)
- 要改配置 → [七、配置完整参考](#七配置完整参考)
- 出问题 → [十二、排查手册](#十二排查手册)

## 一、它是怎么工作的

```
                 ┌──────────────────── 通道①：闸机 / Node-RED ────────────────────┐
Node-RED(1880) ──┤ 一轮十几条消息，只有一条 gate.capture 带「预期结果」           │
或测试程序       │ 用 serial 归轮；按 serial(完整值) 作为唯一序号                  │
                 └──────────────────────────────────────────────────────────────┘
                                          │
被测系统 日志 ──── 通道②：WS 推流 或 跟随日志文件(tail -f) ──┐                  │
                                                            ▼                  ▼
                                             ┌──────────────────────────┐
                                             │ 判定：预期 vs 实际        │
                                             │ 会话ID / 节点 / 旅客 匹配 │
                                             └────────────┬─────────────┘
                                                          │ 不通过
                                                          ▼
                     ┌──────────────────── 串行分析队列（落盘，可断点续跑）────────┐
                     │  DeepSeek Harness headless：读代码 + 日志 + 闸机报文        │
                     │  → analysis.json（根因/证据/方案/改动/修复分支/提交链接）  │
                     └────────────────────────────────────────────────────────────┘
                                                          │
                                      报告 report.html + BI 大屏（http://IP:8767/）
```

要点：

| 概念 | 说明 |
| --- | --- |
| **预期结果** | 闸机/Node-RED 推来的 `gate.capture` 消息（`expected.allow_pass` + `failed_node`） |
| **实际结果** | 从**待测系统日志**里判定：`会话ID[x]-节点y执行失败` → 不允许通行；`旅客[z]离开通道` → 允许通行 |
| **通过标准** | 是否允许通行 **且** 失败节点名称，都与预期一致 |
| **唯一序号** | `serial`（用例号可重复测多次、证号也可能重复，所以只有 serial 唯一） |
| **轮次** | 同一轮十几条消息用 serial 前缀（`serial_1`/`serial_2` → `serial`）归并 |
| **串行** | 分析严格一条一条来：前一条彻底结束（或失败）才开始下一条 |

## 二、常用命令速查

| 我想… | 命令 |
| --- | --- |
| 正常跑起来 | `run_offline.cmd`（或 `python run_autotest.py -c config.yaml`） |

| 先确认两个通道通不通 | `python tools\check_channels.py -c config.yaml --wait 30` |

| 跑 30 分钟自动退 | `python run_autotest.py --duration 1800` |

## 三、主程序 `run_autotest.py`

```bat
python run_autotest.py [-c 配置] [选项]
```

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `-c, --config PATH` | `config.yaml` | 配置文件路径（相对路径按当前目录解析） |
| `--no-dsh` | 关 | 不调用 DeepSeek Harness：只跑测试 + 出报告，失败用例照样入队等以后分析 |
| `--max-analyses N` | 不限 | 本次最多分析 N 条；其余标记为「已达到分析上限」跳过 |
| `--max-cases N` | 不限 | 收到 N 条用例后，等它们判定完、队列清空再优雅退出（自测/CI 用） |
| `--duration SECONDS` | 不限 | 运行 N 秒后自动优雅退出 |
| `--analyze-only` | 关 | 不连 WS、不跑测试，只消费磁盘上已有的队列（离线攒批→联网集中分析） |
| `--drop-pending` | 关 | **启动时丢弃队列里所有「待分析」**，只分析本次新产生的用例 |
| `--log-level LEVEL` | 配置文件值 | `DEBUG / INFO / WARNING / ERROR / CRITICAL` |

### 运行期行为

- **心跳日志**（`run.heartbeat_seconds`，默认 30s）：
  ```
  [心跳] 已收用例 2 条 / 已判定 2 条 / 日志 5158 行·2 会话 / 进行中轮次 2 个·忽略非用例报文 32 条
        / 日志清洗 丢3行·截断18行 / 分析队列 待4·完成0·失败1 / 正在分析 xxx（已 120s）
  ```
  超过 `dsh.timeout_seconds + 300` 会打警告（说明卡在等模型）。
- **Ctrl+C**：停止测试 → **终止正在跑的 DSH**（连进程树）→ 当前分析任务回 `pending`（不算失败尝试）
  → 退出码 130。
- **退出码**：`0` = 没有不通过用例；`1` = 有；`2` = 配置错误；`130` = 被中断。

## 四、队列控制 `tools\queue_ctl.py`

分析队列是**落盘**的（`run.work_dir/run.queue_dir`），所以程序停着也能操作；运行中也有效。

```bat
python tools\queue_ctl.py [-c 配置] <子命令> [选项]
```

### 子命令

| 子命令 | 作用 |
| --- | --- |
| `list` | 列出所有任务（待分析 / 进行中 / 完成 / 失败 / 已丢弃） |
| `drop` | **停止并抛弃**：这些用例不再分析 |
| `requeue-failed` | 把「失败」的任务放回待分析（重试，尝试次数归零） |
| `clear` | 清理历史记录（不动 pending/running） |

### 选项

| 子命令 | 选项 | 说明 |
| --- | --- | --- |
| `list` | `--state pending running done failed dropped` | 只看这些状态（可多选） |
| `drop` | `--all` | 丢弃**全部**待分析任务 |
| | `--case 用例号` | 只丢弃该用例号的任务 |
| | `--running` | **终止正在进行的分析**并丢弃（写取消标记，运行中的程序 2 秒内响应） |
| | `--reason 文字` | 记录丢弃原因（会写进归档与用例状态） |
| `clear` | `--done` / `--dropped` / `--failed` | 清理对应类别的历史记录 |

### 状态与去向

| 状态 | 目录 | 含义 |
| --- | --- | --- |
| `pending` | `_queue/pending/` | 等分析（队列串行，重启后自动继续） |
| `running` | `_queue/running/` | 正在分析；异常退出后启动时自动放回 pending |
| `done` | `_queue/done/` | 分析完成 |
| `failed` | `_queue/failed/` | 尝试次数用尽；`requeue-failed` 可重试 |
| `dropped` | `_queue/dropped/` | **人工抛弃**，不再分析（保留记录便于追溯） |
| `cancel` | `_queue/cancel/` | 取消标记（内部用） |

被丢弃的用例，报告里会显示「已人工放弃分析」，不会一直挂着"等待分析"。

## 五、通道诊断 `tools\check_channels.py`

一条命令回答"为什么没收到用例 / 为什么判不出结论"。

```bat
python tools\check_channels.py [-c 配置] [--wait 秒] [--save-raw 文件] [--only gate,logs,others,http]
```

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `--wait SECONDS` | 15 | 连上后等消息的秒数；**填 0 = 一直等**（Ctrl+C 停止） |
| `--save-raw PATH` | 无 | 把闸机通道收到的**原始报文**完整写入 `.jsonl`（格式对不上时发它即可） |
| `--only LIST` | 全部 | 只查指定部分，逗号分隔。`--only logs` **不连 WebSocket**，几秒出结果，专门核对日志正则 |

它逐项报告：

1. **闸机通道**：能否连上、`mode: both` 时两个方向都试；连上没数据时按五种成因给建议；
   收到的每条消息会校验协议（非用例报文按"正常忽略"处理）；
2. **日志通道**：文件是否存在、**真实编码检测**（GBK/UTF-8）、每条正则各命中几行；
   正则没命中时打印最近 500 行里"可能相关"的真实日志行，并**直接给出可照抄的
   `patterns.passenger_exit` 片段**（已在真实行里验证命中）；
3. **分析/面板**：dsh 能否调用、代码目录对不对（`code_subdir` 重复会明确提示）、面板端口；
4. **HTTP 推用例**：给出可直接复制的 `curl.exe` 示例。

退出码：有 `[FAIL]项` → 1，否则 0。

### `tools\check_dsh.py` — **DSH 调通自检**（手敲能通、程序调用不通时用它）

用**本程序的启动方式**跑一遍 DSH，并把环境差异摊开：

```bat
python tools\check_dsh.py -c config.yaml                  :: 只看入口/环境/dump-config
python tools\check_dsh.py -c config.yaml --ask "你好"      :: 真跑一次模型（验证凭据）
python tools\check_dsh.py -c config.yaml --both           :: cmd 与 direct 两种启动都试
```

| 参数 | 说明 |
| --- | --- |
| `-c, --config` | 配置文件（默认 `config.yaml`） |
| `--ask 提示词` | 真跑一次模型（这一步才会用到凭据） |
| `--both` | 两种启动方式都试（对照用） |
| `--timeout SECONDS` | 单次调用超时（默认 180） |

它会打印：`DSH_HOME` / `DEEPSEEK_API_KEY` / `USERPROFILE` / `APPDATA`、
**从 `dsh.cmd` 解析到的变量**、**所有可能的 dsh home 及哪个有 `.credentials.yaml`**、
实际执行的命令行与工作目录、以及 `--dump-config` 与真跑的结果；
遇到确定性错误（凭据/上下文/端点）会直接给修法。

它的 `[2½] 模型容量` 一节现在还会**真的生成容量 patch 并验证生效**（约 30 秒），
看到 `[FAIL] 容量 patch 没生效` 就别急着跑测试 —— 说明这个 DSH 版本把容量放在别的字段里。

### `tools\check_dsh_capacity.py` — **模型容量专项核对**

专治 `CONTEXT_WINDOW_EXCEEDED`（现场报的是 `17851 + 110150 = 128001`）。
30 秒出结果，不用跑完整测试：

```bat
python tools\check_dsh_capacity.py -c config.yaml              :: 完整核对（推荐）
python tools\check_dsh_capacity.py -c config.yaml --dump-only   :: 只打印当前容量条目
python tools\check_dsh_capacity.py -c config.yaml --keep        :: 保留 dump 原始输出
```

它按顺序做四件事：

1. 跑 `dsh --dump-config`，把**所有与 llm/model 有关的条目**（id + 真实 config）打出来，
   `apiKey` 之类的值自动打码；
2. 用本程序的逻辑生成容量 patch，并把 patch 内容打印出来；
3. 带上 patch 再 dump 一次，把同样的条目再打一遍；
4. 对比前后数值，直接给结论：**生效** / **没生效**，并给出下一步。

> 什么时候必须用它：日志里出现 `⚠ 容量 patch 已生成但**没生效**`、
> 或者 `check_dsh.py` 报 `[FAIL] 容量 patch 没生效`。

## 七、配置完整参考

配置文件为 YAML，**未知键会直接报错**（并提示最接近的正确键名），避免"写了却没生效"。
路径类配置支持相对写法，**按配置文件所在目录**解析。

### 7.1 `run` — 运行参数

| 配置项 | 默认 | 说明 |
| --- | --- | --- |
| `work_dir` | `./runs` | 产物根目录：`<work_dir>/<批次>/cases/<用例>/...` |
| `case_timeout_seconds` | `25` | 单条用例等日志结论的最长时间（秒）。真实闸机流程建议 60~120 |
| `max_buffer_lines` | `200000` | 日志缓冲区上限（超过丢最旧的） |
| `capture_tolerance_lines` | `5` | 用例归属时允许"会话创建行"超前/滞后的行数容差 |
| `slice_include_passenger_lines` | `true` | 日志切片是否包含 `旅客[xxx]` 相关行（保证"离开通道"在报告里） |
| `queue_dir` | `_queue` | 分析队列目录（相对 `work_dir`） |
| `analysis_max_attempts` | `2` | 单条分析最多尝试次数 |
| `max_slice_lines` | `1500` | 单条用例最多抽多少行日志交给模型 |
| `slice_lead_lines` | `60` | 日志切片在「会话起点」那行**再往前多带几行**上下文。锚点取 `min(创建新会话行, 第一次出现该会话ID的行)`，所以"创建新会话"那行格式和正则不符时也不会漏掉前面 |
| `single_session_fallback` | `true` | 找不到旅客标识、但只有一个严格更晚的候选会话时，按它归属 |
| `heartbeat_seconds` | `30` | 心跳日志间隔（最小 5） |

### 7.2 `gate` — 通道①（用例 + 预期结果）

| 配置项 | 默认 | 说明 |
| --- | --- | --- |
| `mode` | `client` | `client`=我们去连它；`server`=我们监听；**`both`=两个方向都收**（推荐排查看不清方向时用） |
| `url` | `ws://127.0.0.1:8765/gate` | `client`/`both` 时我们连的地址 |
| `listen_host` | `127.0.0.1` | `server`/`both` 时监听地址（`0.0.0.0` 允许局域网） |
| `listen_port` | `8765` | 监听端口 |
| `listen_path` | `/gate` | 监听路径 |
| `reconnect_seconds` / `max_reconnect_seconds` | `3` / `30` | 断线重连（指数退避） |
| `ping_interval` | `20` | 心跳间隔（`null` 关闭） |
| `headers` | `{}` | 握手鉴权头，如 `{Authorization: 'Bearer xxx'}` |
| `send_ack` | `true` | 收到用例是否回 `{"type":"gate.ack",...}`；**不想扰动对方流程就设 false** |
| `subscription` | `null` | 连上后立刻下发的报文（有些中继要先订阅） |
| `field_map` | `{}` | 对方字段名不同的翻译表：`{本程序字段: 对方点路径}`，例 `{allow_pass: msg.payload.allow}` |
| `round_keys` | `[serial, Serial, serialNo, serial_no, requestId, request_id, capture.serial, capture.cert_no, cert_no]` | 依次取第一个非空值作为"轮次/唯一序号"来源 |
| `round_split` | `'_'` | 轮次键含该字符时只取前半段（`serial_1`/`serial_2` 同轮）；`null` = 不切分 |
| `round_ttl_seconds` | `600` | 多久没动静就忘掉这条轮次记录 |

### 7.3 `logs` — 通道②（待测系统日志）

| 配置项 | 默认 | 说明 |
| --- | --- | --- |
| `source` | `ws` | `ws` = WebSocket 推流；`file` = 跟随日志文件 |
| `url` | `ws://127.0.0.1:8766/logs` | `source: ws` 时的地址 |
| `reconnect_seconds` / `max_reconnect_seconds` | `3` / `30` | 重连退避 |
| `ping_interval` | `20` | 心跳 |
| `headers` | `{}` | 握手头 |
| `message_format` | `auto` | `auto` / `text` / `json` |
| `text_fields` | `[line, text, message, msg, content, log]` | JSON 包体里正文的字段（支持 `a.b`） |
| `subscription` | `null` | 连上后下发的订阅报文 |
| `max_field_chars` | `100` | 单行里超过该长度的字段只保留前 N 字符并标注总长（`0` = 不截断） |
| `drop_undecodable` | `true` | 清掉行内的**乱码片段**（`？？？？旅客离开通道` → `旅客离开通道`）；只有整行都是乱码时才丢整行。设 `false` 则完全不清洗 |
| `file.path` | `null` | `source: file` 时的日志路径（**必填**） |

### 7.4 `patterns` — 日志识别正则（**判定全靠它**）

> 三项正则都可以写**一条**，也可以写**一组**（YAML 列表）：任意一条命中就算命中。
> 被测系统换版本改了措辞时，往列表里加一条即可，**不用改代码**。

| 配置项 | 默认 | 说明 |
| --- | --- | --- |
| `session_create` | `\[流程引擎\]\s*创建新会话[：:\s]*\[?(?P<sid>[^\s\[\]，,。;；]+)\]?` | 会话起始行，需捕获 `sid` |
| `node_failure` | `会话ID\[(?P<sid>[^\]]+)\]\s*[-—－–:：]\s*节点\s*(?P<node>.+?)\s*执行失败` | 节点失败，捕获 `sid` + `node` |
| `passenger_exit` | 一组（见下） | 允许通行的结论事件，捕获 `key`（可缺省） |
| `passenger_marker` | `旅客\[(?P<key>[^\]]+)\]` | 通用旅客标记（用于避免认领别人的会话） |

`passenger_exit` 的默认值是一组，覆盖实际现场见过的写法：

```yaml
patterns:
  passenger_exit:
    - '旅客\[(?P<key>[^\]]+)\][^\n]{0,16}?离开通道'        # 旅客[xx]已离开通道 / 离开通道，提交成功
    - '旅客\[(?P<key>[^\]]+)\][^\n]{0,16}?(?:已放行|开闸成功|闸门已开)'
    - '离开通道'                                          # 整行没有 旅客[...] 标记
    - '(?:已放行|开闸成功|闸门已开)'
```

要点：

* `[^\n]{0,16}?` 负责容错 —— `已离开通道`、`离开通道，提交成功` 这类"多几个字"仍然命中；
* 列表里**前面的带 `key` 的优先**，匹配到的 `key` 用于和用例字段（证号/姓名）对号；
* 最后两条不带 `key` 的兜底只在"没有更精确的匹配"时生效，归属退化为**会话区间**判断；
* 新版本只打「提交成功」这类没见过的措辞时，加一条 `- '提交成功'` 即可。

**不知道怎么改的时候，先跑这条命令（不连 WebSocket，几秒出结果）：**

```bat
python tools\check_channels.py --only logs
```

它会把 `最近 500 行` 的命中数、以及**没命中时日志里的真实行样**打印出来，照抄进列表就行。

**自动容量收敛**：每次分析前 `--dump-config`（有缓存、60s 超时）读出当前组合，
生成一份 `dsh-model-capacity.patch.yml`，把 DSH 认为的容量压到安全范围，
避免 `CONTEXT_WINDOW_EXCEEDED: requested 110046 output + 17955 input > 128000`。

> **`models[]` 必须显式写**（现场踩得最狠的一次）：`dsh --dump-config` **不打印
> schema 默认值**，而 `llm-deepseek` 的默认 `models[]` 里每个模型都自带
> `contextWindow`（现场是 128000），目录值的优先级**高于** `defaultContextWindow`。
> 所以只写 `defaultContextWindow: 103424` 等于没写 —— 端点照样按 128000 算输出上限，
> 每次都是"输入 + 输出 = 128001"。现在 patch 会把 `models[]` 一起写出来。

**端点上下文 128k 时的推荐写法**：

```yaml
dsh:
  context_window: 128000     # 端点真实上下文
  max_tokens: 24000          # 输出上限（剩下 ~100k 全给输入）
  # input_reserve_tokens: 32768   # 想更保守就调大
  context_headroom_tokens: 24576  # 声明上下文 = 128000 − 24576 = 103424
```

### 为什么这样就不会再撞 `CONTEXT_WINDOW_EXCEEDED`

现场几次报错都是**刚好超 1**：

```
17955 + 110046 = 128001      30198 + 97803 = 128001      17851 + 110150 = 128001
```

说明端点把"输出上限"算成了 `上下文 − 输入`（DSH 的 `maxTokens` 这一版没被采纳）。
所以在**上游**保证：patch 里把 `contextWindow` 声明的比真实上限小 `context_headroom_tokens`。
这样即使 `maxTokens` 被忽略，输入 + 输出也只等于"缩小后的上下文"：

| 场景 | 计算 | 结果 |
| --- | --- | --- |
| `maxTokens` 被采纳 | 30198 + 24000 | 54198 ✅ |
| `maxTokens` 被忽略（最坏情况） | 30198 + (103424 − 30198) | 103424 ✅ 仍在上限内 |

（`103424 = context_window 128000 − context_headroom_tokens 24576`，是 patch 里声明的**假上下文**。
真上限 128000 比它大，所以无论端点怎么算都不会溢出 —— 这就是"足够余量"的数学保证。）

再加四层保险：

1. `dsh --dump-config` 后只改**确实支持这些字段的插件**（`llm-deepseek` 的
   `maxTokens`/`defaultContextWindow`/`models[]`、`llm-pi-ai` 的 `providers.<route>.models[]`），
   其它插件一律不动 —— 往 schema 不认识的插件塞键会让 **DSH 启动即崩**；
2. 还有一层**通用兜底**：dump 里别的条目若本来就带 `maxTokens`/`contextWindow`，
   只改**已有的值**（绝不新增键 → 不可能因为 schema 崩）；
3. 生成的 patch **先自检再使用**：`--patch … --dump-config` 能跑通（不崩）**并且
   dump 里确实出现我们要的数值**才算通过。以前只检查"dump 里有没有这个词"，
   那个条件永远为真 —— 于是"自检通过"但完全没生效，白等 40 分钟才在端点报 400；
4. 万一仍然报 `CONTEXT_WINDOW_EXCEEDED`，程序会**自动把声明上下文再压 25% 重试一次**。

自检命令（会真的生成 patch 并验证生效，约 30 秒，不用跑完整测试）：

```bat
python tools\check_dsh.py -c config.yaml              :: 全套自检，含容量是否生效
python tools\check_dsh_capacity.py -c config.yaml     :: 只看容量：dump 前后的真实条目对比
python tools\check_dsh_capacity.py -c config.yaml --dump-only   :: 只打印当前容量条目
```

`[2½] 模型容量` 一节会列出每个模型条目的 `maxTokens/contextWindow`，超限的直接标 `[FAIL]`。
若看到 **`[FAIL] 容量 patch 没生效`**，说明这个 DSH 版本不吃我们改的字段 ——
把 `check_dsh_capacity.py` 打印的 `[1]` 那段（或 `--keep` 留下的 `dump-before.yml`）发给我即可。

## 九、判定与数据关联规则

1. **会话归属**：从 `[流程引擎]创建新会话<会话ID>` 到最后一次出现该 ID；
   用采集信息里的 `passenger_keys` 去匹配 `旅客[xxx]` 认领会话；匹配不上时按
   **"采集时已经在运行的会话"** 归属（并发时 A 还在跑后面的节点、B 已经开始前面的节点，
   也能各归各的，不会把 A 的前半段丢掉）。`session_id`（用例消息里指定）优先级最高。
2. **会话ID 清洗**：`创建新会话（12345）`、`[12345]`、`「12345」`、`"12345"` 这些包裹符号
   会自动剥掉，避免和 `会话ID[12345]` 对不上导致「0 会话」。
2. **判定**（日志侧）：
   - `会话ID[x]-节点 y 执行失败` → 实际不允许通行，失败节点 = y
   - `旅客[z]离开通道` → 实际允许通行
   - 超时未见任一 → 「未获取到有效日志」，判不通过并进入分析
3. **轮次与唯一序号**：`round_split` 前面的前缀 = 轮次；**完整 serial** = 唯一序号（目录名/队列任务）。
4. **日志切片起点**：锚点 = `min(创建新会话行, 第一次出现该会话ID的行)`，再往前带
   `slice_lead_lines` 行；终点是该会话 ID 最后一次出现的位置。
   **超过 `max_slice_lines` 时头尾各留一半**（中间插一行"……（中间省略 N 行）……"），
   保证会话开头和结论都在。完全没匹配到会话时，按"采集点前 `slice_lead_lines` 行 + 之后尽量多"截取。
5. **日志清洗**：抠掉行内**乱码片段**（`？？？？旅客离开通道` → `旅客离开通道`），
   只有整行都是乱码才丢；长字段截断到 `max_field_chars` 并标注 `…（长字段共 N 字符）` ——
   提示词里也告知模型"这是截断，不是 bug"。
6. **分析过程可见**：分析进行中，报告第五节会滚动显示模型的实时输出（stdout + reasoning），
   并在 `cases/<用例>/analysis_live.log` 留全文；分析结束后报告只展示结构化结论。

## 十二、排查手册

| 现象 | 先做什么 | 说明 / 常见原因 |

| 一条用例都没收到 | `python tools\check_channels.py --wait 30` | 地址/路径错；对方只回给发起方（见第十节）；需要订阅（`gate.subscription`） |
| 连上了但没数据 | 同上，加 `--save-raw gate_raw.jsonl` | 用 `gate.mode: both` 两个方向都试 |
| 收不到预期结果报文 | 看 `gate_raw.jsonl` | 一轮十几条里只有一条带 `expected`；用 `field_map` 翻译字段名 |
| 日志明明有内容却判不出 | 看诊断的"编码检测"和正则命中数 | 编码错（设 `auto`）；正则与真实文案不符 |
| 判定总是「不允许通行」 | 看 `cases/<用例>/logs.txt` | `patterns.node_failure` 与真实日志不符 |
| **旅客明明正常通行了，却判「没检测到结论」/超时** | `python tools\check_channels.py --only logs` | 新版本改了措辞（`已离开通道`、`提交成功`、整行不再带 `旅客[...]`）。诊断会把真实行样打印出来，照抄进 `patterns.passenger_exit` 列表即可；心跳日志里出现"已读到日志但没识别到任何结论事件"就是这一条 |
| 用例超时 | 调大 `case_timeout_seconds` | 真实闸机流程 60~120 秒更稳妥 |
| 分析队列不动 | `python tools\queue_ctl.py list` | 看是否有 `running` 卡住；`drop --running` 后重试 |
| 报 `CONTEXT_WINDOW_EXCEEDED` | 无需处理（已自动收敛） | 若仍出现：先跑 `python tools\check_dsh_capacity.py -c config.yaml`，看是不是"patch 没生效"（这个 DSH 版本不吃这些字段）；再把 `max_slice_lines` 调小 |
| **日志里出现"容量 patch 没生效"** | `python tools\check_dsh_capacity.py -c config.yaml --keep` | 把打印的 `[1]` 段（或 `dump-before.yml` 里 id 含 llm 的条目）发给我，我按你的版本改写法 |
| 报「分析结束但没有生成 analysis.json」 | 看该用例的 `dsh_stderr.log` + `analysis_prompt.md` | 模型没读到任务（参数被截断）/ 没按 JSON 输出 |
| **模型很慢，分析到一半被掐断** | `dsh.timeout_seconds: 0`（不限总时长）+ `dsh.idle_timeout_seconds: 1800` | 只有"连续很久没有任何输出"才算卡死；模型还在出字就一直等。超时时如果已经写出 `analysis.json`，也会按成功收下 |
| **分析特别慢（动辄几十分钟）** | 看 `analysis_live.log` 里模型在干什么 | 常见原因：模型反复分块读 `logs.txt`/`gate_messages.jsonl` 找"被省略的中间部分"。提示词里已给出「关键事件摘要」并明确禁止反复分块读；仍慢可减小 `max_slice_lines`、关掉 `dsh.repo_map` |
| **手敲 `dsh` 能通，程序调用报 MISSING_CREDENTIAL** | `python tools\check_dsh.py -c config.yaml --ask "你好"` | 多半是环境差异：`dsh.cmd` 里的 `set DSH_HOME=…` 没生效。程序默认用 `cmd /c` 调 `.cmd`（与手敲一致）；若把 `dsh.launch_mode` 改成 `direct` 则会绕过 cmd，可能丢这些变量（程序会自动解析 `.cmd` 里的 `set` 补上） |
| 想让某些分析不再跑 | `python tools\queue_ctl.py drop --all` | 或启动时 `--drop-pending` |
| 停止程序时 DSH 还在跑 | 不会（已修）：直接启动 node + `taskkill /T` 兜底 | 日志会打印"已终止 N 个 DSH 分析进程" |
| 修复提交找不到链接 | 检查 `git remote get-url origin` | 无远端就不生成链接；SSH/https/带端口都支持 |
| 面板打不开 | `python tools\check_channels.py` 看端口 | 端口被占用；`report.port: 0` 可自动分配 |
| 换机器跑不起来 | `python tools\verify_offline.py` | 依赖/DSh 路径/凭据问题 |
